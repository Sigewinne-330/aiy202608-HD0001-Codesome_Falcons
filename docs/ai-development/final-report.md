## 5. Email Verification APIs

### Added

- `POST /api/auth/verification-codes`
  - Input: email.
  - Success: HTTP 202 generic response and resend delay.
  - Rate limit: HTTP 429 with `Retry-After`.
  - Eligible-email provider failure: HTTP 503 and an unusable challenge.

- `POST /api/auth/verification-codes/verify`
  - Input: normalized email and 6-digit code.
  - Success: short-lived opaque `verification_token`.
  - Invalid/expired/old/used/locked code: generic HTTP 400.

### Modified

- `POST /api/auth/register`
  - Now requires `verification_token`.
  - The proof must be unexpired, unconsumed, and issued for the same normalized email.
  - Proof consumption and user creation commit atomically.
  - Successful JWT/user response is unchanged.

Login, `/me`, JWT shape, and authenticated product APIs remain compatible.

## 6. Database Changes

Added `email_verifications` with:

- normalized email and request IP;
- per-row salt and HMAC-SHA256 code digest;
- unique SHA-256 registration-token digest;
- delivery state and failed-attempt count;
- code/proof expiry, verification, invalidation, and consumption timestamps;
- indexed `(email, created_at)` and `(request_ip, created_at)` history lookups.

The change is non-destructive and creates no new foreign key to the existing `user` table. Existing users require no migration.

## 7. Security Considerations

- No plaintext code or registration proof is persisted or returned by the request-code API.
- Six-digit codes use HMAC-SHA256 with the application secret and per-row random salt.
- Registration proofs are high-entropy, hashed, email-bound, expiring, and single-use.
- Only the newest successful request remains valid, including out-of-order concurrent delivery completion.
- Failed guesses are bounded and lock the challenge.
- Resend cooldown and rolling email/IP limits persist in the database.
- Registered-email requests are generically suppressed and share the same email limits without sending mail.
- Email failures/timeouts/invalid headers invalidate the challenge and disclose no code.
- Source IP comes from the direct connection; untrusted forwarded headers are ignored.
- Backend Pydantic validation remains authoritative.
